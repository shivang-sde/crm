# L3.4-P4 — Customer Health Readiness & Signal-Quality Audit

**Scope:** read-only audit of the Customer Health implementation after L3.4-P1, P2 and P3.
**Date of audit:** 2026-10-22
**Auditor:** automated, evidence-based (no production code, schema, contract or fixture changes)

---

## 1. Executive verdict

**Composite Customer Health scoring: `NOT READY`.**

The signal layer is a good *explanatory list* of individually-cited facts, but it is not a
sound input to a composite score:

- one signal is objectively wrong on the cross-account endpoint (`ENGAGEMENT_FEEDBACK_SILENT`);
- one signal filters on the wrong timestamp (`RECENT_DEAL_LOSS` uses deal creation, not loss);
- two signals have no rule-level test at all (`HIGH_CES`, `RECENT_DEAL_LOSS`), and all four
  feedback predicates are untested because the test harness cannot evaluate Specifications;
- entitlement expiry produces one signal per historical period and can be suppressed by a
  future-dated `PENDING` row across a coverage gap;
- the same account yields different signal sets to different users (per-domain record scope),
  so a score would not be stable or comparable;
- three of the seven requested health dimensions have **no authoritative data at all**
  (financial, product usage, account/data completeness);
- there is **no documented severity, weighting, or scoring policy** in the repository.

**Signal API as a triage listing: `READY WITH CAVEATS`** — see per-signal verdicts in §3.

### Verification notes per signal

**1–4 Feedback signals.** The predicate lives entirely in a JPA `Specification`
(`RiskSignalService.java:191-211`, `scoreRange` at `:229-238`). Unlike the entitlement rule,
the service does **not** re-check type or score in Java. The test harness acknowledges this:
“a mock cannot filter by Specification” (`RiskSignalControllerTest.java:626-628`, `:812-819`).
The helper `givenFeedbackScore` is declared but **never called** (1 occurrence = declaration),
so no test exercises any feedback predicate. The three tests that do stage feedback
(`giveFeedbackAged`) also produce spurious `NEGATIVE_NPS`/`LOW_CSAT`/`HIGH_CES`/`RECENT_COMPLAINT`
signals because the mock returns the same row to all four queries; those tests only assert
`contains`/`doesNotContain` on `ENGAGEMENT_FEEDBACK_SILENT`, so the extra signals are invisible
to the assertions. `FeedbackSource.INTERNAL` (“captured by CRM staff”, `FeedbackSource.java:37`)
is not filtered out, so staff-mediated input counts as customer sentiment.

**5 SLA breach.** `RiskSignalService.java:443-471` filters only `sla_breached = true`. There is
no status filter and no window. `TicketSlaBreachService` sets the flag on a missed response or
resolution deadline; `V73__add_ticket_sla_fields.sql:34-35` documents that the flag is
historical and never cleared on resolve/close. The breach type (`RESPONSE`/`RESOLUTION`) is
published only in event metadata (`TicketSlaBreachService`, `breachTypeFor`), not persisted on
the row. `V73` has no index on `sla_breached = true`.

**6 Approaching expiry.** `RiskSignalService.java:523-564`, boundaries at `:555-559`.
`isLiveCoverage` (`:605-612`) requires `ACTIVE|PENDING` and `endDate >= today`; only `ACTIVE`
emits (`:552-554`). `expiresSoon` is `!endDate.isAfter(horizon)`, i.e. inclusive of `today+30`.
`PENDING` never emits, by design. `detectedAt` is `createdAt` (`:685`), so an entitlement that
enters its window this month reports a timestamp from when it was sold.

**7 Expired.** `RiskSignalService.java:566-591`, `coverageKey` at `:620-626`,
`isLiveCoverage` at `:605-612`. `endDate <= today-1` is the `LocalDate` equivalent of
“strictly before today”. Suppression only checks the later row’s `endDate`, never its
`startDate`.

**8 Deal loss.** `RiskSignalService.java:718-741`; the window predicate is on
`root.get("createdAt")` (`:730-737`) and the query sorts by `createdAt` (`:743-745`). The
authoritative loss time exists: `Deal.closedDate` is set on close
(`DealService.java:1023`) and `Deal.stageEnteredAt` is set on stage change
(`DealService.java:132,360,682`); `idx_deal_closed_date` exists
(`V10__create_deal_tables.sql:103`). `detectedAt` is the deal’s creation time (`:754`).

**9 Feedback silence.** `RiskSignalService.java:275-325`. The account predicate is added only
when `accountId != null` (`:289-291`); the query is always `PageRequest.of(0, 1, DESC createdAt)`
(`:293-296`). On the cross-account route `accountId` is `null`
(`RiskSignalController.java:100-101`), so the spec is tenant-wide and the limit is one: the
returned row is the tenant’s **newest** feedback. If that row is newer than `from` the method
returns nothing for the whole tenant; if it is older, exactly one signal is emitted, for the
account that engaged **most recently**. Every other previously-engaged account is invisible.
The trigger also depends on the caller’s `from` (default `now-30d`,
`AnalyticsDateRange.java:15,32-43`); `to` is ignored.

**10–12 Support.** `RiskSignalService.java:342-433`. Status and `now` are re-checked in Java
(`:368-372`). `SUPPORT_NO_RESPONSE_PAST_DUE` uses `!now.isBefore(responseDueAt)` (`:378`), so
“due exactly now” is overdue; `SUPPORT_SLOW_FIRST_RESPONSE` is the `else` branch (`:392-410`);
`SUPPORT_PAST_RESOLUTION_DUE` uses `!now.isBefore(resolutionDueAt)` (`:413`). All three use the
ticket’s own snapshotted deadlines, so no threshold is invented. `detectedAt` is `createdAt`
for #10 and #12, `firstResponseAt` for #11.

## 4. Cross-signal consistency and false-positive analysis

### 4.1 `ENTITLEMENT_EXPIRED` vs `ENTITLEMENT_APPROACHING_EXPIRY`

Mutually exclusive in practice: the expired rule requires `status = EXPIRED` and
`endDate < today`; the approaching rule requires `status = ACTIVE` and `endDate >= today`.
There is no duplicate. Two blind spots are intentional and documented
(`RiskSignalService.java:516-521`):

- an `ACTIVE` row whose `endDate` has passed is reported by **neither** rule (status is the
  lifecycle contract; the scheduler is expected to flip it);
- an `EXPIRED` row with `endDate == today` is reported by **neither** rule.

Both become real gaps if the expiry scheduler is disabled or lagging.

### 4.2 P3 suppression — what the code actually does

`ENTITLEMENT_EXPIRED` is suppressed when `coveringKeys` contains the same
`accountId|offeringId` (`RiskSignalService.java:540-577`), where a key is added for every
`ACTIVE|PENDING` row that `isLiveCoverage` accepts:

| Later coverage | Suppresses? | Consequence |
|---|---|---|
| `ACTIVE`, `endDate >= today` | yes | correct |
| `PENDING`, `startDate` in the future, `endDate >= today` | **yes** | **a coverage gap is hidden**; the test `forwardDatedRenewalCountsAsRecordedCoverage` pins a 3-month gap |
| `PENDING`/`ACTIVE` with `accountId` or `offeringId` null | no (key is `null`, `:622-624`) | false positive |
| soft-deleted later coverage | no (`buildSpecification:52`) | correct (cannot hide the lapse) |
| `CANCELLED`, `TERMINATED`, `SUSPENDED`, `EXPIRED` later coverage | no | false positive when coverage was deliberately replaced/suspended |
| same offering, **different tenant** | no (tenant predicate) | correct |
| renewal into a **different offering** | no | documented limitation, pinned by `laterCoverageForADifferentOfferingDoesNotMaskTheLapse` |

Because `isLiveCoverage` never inspects `startDate`, a forward-dated renewal suppresses the
lapse for its entire lead time, including any uncovered interval. Conversely, every historical
expired period for the same offering emits its own signal when no live coverage exists — a
customer with five annual terms and one lapse gets five `ENTITLEMENT_EXPIRED` signals, not one.

### 4.3 `RECENT_COMPLAINT` vs NPS/CSAT/CES

One feedback row has exactly one `type`, so a single methodology response cannot produce two
sentiment signals. Two rows about the same event (e.g. `COMPLAINT` plus `CSAT=1`) produce two
signals with no correlation key beyond account and time. `ComplaintTicketService` can convert a
complaint into a Ticket (`ComplaintTicketService.java:101-112`), so the same customer event can
additionally produce `SLA_BREACHED_TICKET` and/or `SUPPORT_*` from the derived ticket. These are
correlated, not independent evidence.

### 4.4 SLA-breach vs support-deadline signals

Same ticket, same root fact, up to two signals:

- `SLA_BREACHED_TICKET` (HIGH, permanent, all statuses) is driven by the persisted flag;
- `SUPPORT_PAST_RESOLUTION_DUE` (MEDIUM, open work only) and `SUPPORT_SLOW_FIRST_RESPONSE`
  (MEDIUM) are evaluated live.

While the ticket is open and past its resolution deadline, both fire. Once the ticket is
resolved, only the HIGH signal remains. If the breach scan is disabled
(`app.tickets.sla.breach-scan-enabled`, `application-prod.yml:85`), the same reality produces a
different set of signals — the result depends on scheduler configuration, not just data.
A late first response on a ticket that has since closed produces **no** signal at all, because
the status check (`:368-372`) runs before the slow-response branch.

### 4.5 `ENGAGEMENT_FEEDBACK_SILENT` vs other engagement indicators

There are no other engagement indicators. The repository has no inbound email, portal,
web-analytics, meeting-attendance or product-usage trail; `CALL` activities record that a rep
pressed dial (`DefaultClickToCallService`, subType `CALL_INITIATED`), not that a conversation
happened. On the account route the signal is coherent (“demonstrably gave feedback before, none
inside the window”). On the cross-account route it is inverted (§3 note 9). “Silent” and
“negative NPS” can coexist for the same account, because they read different rows.

### 4.6 `RECENT_DEAL_LOSS` vs entitlement and account lifecycle

A lost renewal deal and the resulting expired entitlement are the same commercial event, but
they are not linked: `renewal_deal_id` is never written. The deal rule’s `createdAt` window
makes the two easy to desynchronise — an old deal lost yesterday produces
`ENTITLEMENT_EXPIRED` (or approaching expiry) but no `RECENT_DEAL_LOSS`.

### 4.7 Absence of a signal does not mean good health

- no feedback rows ⇒ no sentiment signal **and** no silence signal;
- no tickets ⇒ no support signal;
- no entitlements ⇒ no lifecycle signal;
- no lost deals ⇒ no commercial signal;
- a resolved/closed ticket ⇒ slow-response history disappears;
- a brand-new account with no records at all yields **zero signals** and would look perfect
  under any count-based score.

Severity is not a function of time-to-now: old facts never decay, and nothing is acknowledged,
snoozed or resolved.

**Engineering readiness vs business-policy readiness.** The plumbing to compute facts is ready
(injected clock, bounded queries, source references). The business policy is not: no documented
severity definitions, no dimension weights, no thresholds for “healthy”, no decay or
acknowledgement model, no aggregation rules. No weights or formula are recommended here because
no defensible policy exists in the repository.

## 6. API, tenancy, security, performance findings

### Verified controls

- **Authentication/authorization:** both routes require a valid bearer token and `account:read`;
  `RbacFilter` maps `customer-health` → `account` (`RbacFilter.java:315`).
- **Tenancy:** `TenantContext.requireTenantId()` is the only tenant source; every source
  specification filters `tenant_id`.
- **Record scope:** resolved per source domain from that domain’s own module
  (`RiskSignalService.java:102-105`); an unseeded/unknown scope yields `cb.disjunction()`
  (fail-closed). Tests: `supportSignalsRespectTicketScope`,
  `withholdingASourcePermissionSuppressesOnlyThatDomain`,
  `sourceDomainsWithoutPermissionContributeNoSignals`,
  `entitlementSignalsRespectEntitlementScope`, `teamScopeResolvesTheTeamOnceAndStillReturnsSignals`,
  `ownScopeNeedsNoTeamLookup`.
- **Soft delete:** excluded for all four sources.
- **Determinism:** injected `Clock`; tests use `Clock.fixed(2026-06-01T00:00:00Z)`.
- **N+1:** none. Metadata is built from the row already loaded.
- **Bounded reads:** 10 queries per request, each capped at 500 rows.

### Findings

1. **Per-user scope makes the output non-comparable.** The same account produces different
   signal sets for an ALL, TEAM and OWN user. A composite score built from this would differ by
   viewer and could not be audited against a single value.
2. **The account route does not verify account visibility** — it applies the caller’s
   per-source scope, not an account-level `visibleToUser`. A user who owns one ticket for an
   account can receive signals for that account without being able to open it. This is
   documented as intentional (`RiskSignalService.java:44-49`) but is a scoring hazard.
3. **`accountId` is not “always present”** as the DTO claims (`RiskSignalResponse.java:23-24`):
   `deals.account_id` and `customer_entitlements.account_id` are nullable, so deal-loss and
   entitlement signals can carry `accountId = null`; the cross-account listing then contains
   unattributable rows.
4. **Silent truncation.** Each source query takes the first 500 rows; `meta.total` and
   `totalPages` are computed from what was loaded (`RiskSignalController.java:100-116`). A
   tenant with more than 500 rows in any source receives an incomplete list presented as
   complete. Cap ordering is inconsistent: `supportHealth` sorts `createdAt ASC` (keeps the
   oldest) while `slaBreachedTickets` sorts `createdAt DESC` (keeps the newest).
5. **Cross-account filtering is in memory.** Type/severity are applied after all 10 queries and
   after loading up to 5 000 rows, then sorted (`RiskSignalController.java:100-105`). A
   `?type=ENTITLEMENT_EXPIRED` request still runs every query.
6. **Page overflow can 500.** `int fromIndex = Math.min(safePage * safeSize, matching.size())`
   (`RiskSignalController.java:107`) overflows for large `page`, producing a negative index and
   an `IndexOutOfBoundsException`. The clamp test only covers `page=-5`, `size=100000`.
7. **Window semantics are inconsistent.** The Javadoc promises half-open `[from, to)`
   (`RiskSignalService.java:84-87`), but feedback and deal filters use `cb.between`, which is
   inclusive of `to` (`:202`, `:734`). `SLA_BREACHED_TICKET`, all support signals and all
   entitlement signals ignore `from`/`to` entirely — the account route’s `from`/`to` therefore
   filters only some of the returned signals.
8. **Index coverage.** Feedback `(tenant,type,created_at DESC)` and tickets `(tenant,status)`
   exist; entitlements have `(tenant,status,end_date)`. There is **no** index for
   `tickets.sla_breached = true`, so the P1 rule degrades to a scan on large tenants.
   The deal-loss rule filters `deals.created_at`, for which `idx_deal_created_at` exists; the
   natural `closed_date` index (`idx_deal_closed_date`) is unused because the predicate is wrong.
9. **Logging/observability.** One `log.debug` per request (`RiskSignalService.java:133`). No
   metrics, no per-rule counts, no query timing, no “as of” timestamp in the response. An
   unexpected signal can be traced to its source row, but not to why a rule fired at scale.
10. **No integration surface.** `RiskSignalService` has exactly one consumer, the controller
    (grep: 2 call sites, both in `RiskSignalController`). There is no Customer 360 section, no
    frontend usage (`grep -r "customer-health|health/risk" frontend/src` → 0 matches), no
    scheduled notifier, and no acknowledgement/resolution state.
11. **Dead dependency.** `RecordScopeGuard` is injected into `RiskSignalService` but never used
    (`RiskSignalService.java:29,77`).
